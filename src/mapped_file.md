# Memory-Mapped File Wrapper & LRU Cache (`mapped_file`)

## Goals & Responsibilities
The `mapped_file` class (`src/mapped_file.h`, `src/mapped_file.cpp`) provides a reusable C++23 RAII read-only file mapping abstraction, zero-copy line indexer, and refcounted LRU cache with background readahead:
- **Zero-Copy Virtual Memory Mapping (`mmap`)**: Maps regular files into the process address space with `PROT_READ, MAP_PRIVATE` and closes the underlying file descriptor immediately after `mmap` succeeds.
- **Opt-In Page Prefaulting & Hugepages (`populate`)**: When `open(path, out_error, /*populate=*/true)` is requested, passes `MAP_POPULATE` (for files $\le 64\text{ MB}$), attempts `MAP_HUGETLB` with transparent fallback + `madvise(..., MADV_HUGEPAGE)` for files $\ge 2\text{ MB}$, and advises `MADV_WILLNEED`.
- **Transparent Heap Fallback**: If `mmap` fails (for example on virtual/FUSE filesystems that do not support memory mapping or when `vm.max_map_count` is exhausted), `mapped_file::open` transparently falls back to allocating a `std::vector<uint8_t>` and reading the file via `::read`.
- **In-Memory `is_binary()` & Zero-Copy `lines()`**:
  - `is_binary(bool treat_null_as_binary = true)` classifies the first 4,096 bytes in memory during `open()`, eliminating the separate `open` + `read(4096)` syscall previously performed by text tools.
  - `lines()` splits the buffer into `std::span<const std::string_view>` using a single vectorized `std::memchr` pass (stripping trailing `\r`), protected by `lines_mutex_` + `lines_ready_` for thread-safe sharing across concurrent readers.
- **Refcounted 64-Entry LRU Cache & Bounded Readahead (`get_cached`, `notify_changed`, `prefetch`)**:
  - `mapped_file::get_cached` returns a `std::shared_ptr<const mapped_file>` validated via `stat()` (`st_dev`, `st_ino`, `st_size`, `st_mtim`).
  - `mapped_file::notify_changed` proactively evicts modified files and, if the file was hot in the cache, enqueues it at the front of the background readahead worker queue to re-warm the mapping and line index immediately.
  - `mapped_file::prefetch` enqueues up to `k_max_prefetch_window` (24) paths into a background worker thread (stopped cleanly via `mapped_file::shutdown_cache()` in `project_manager::shutdown()`), ensuring readahead never overruns the 64-entry cache before consumption.

## Constraints & Lifetime Safety
- **Move-Only Value / Refcounted Shared Ownership**: Direct `mapped_file` instances are non-copyable and movable; cached instances are shared via `std::shared_ptr<const mapped_file>` so concurrent readers retain their `MAP_PRIVATE` mapping even if a newer edit replaces the cache entry.
- **Compile-Time Dangling-View Prevention**: Rvalue conversion overloads (`const &&`) for `bytes()`, `string_view()`, and `lines()` are explicitly `= delete`d so callers cannot accidentally bind a `std::span` or `std::string_view` to a temporary `mapped_file`.

## Lessons Learned
- **Eliminating Arbitrary 50MB Caps & Redundant Line Scans**: Tools like `fs_read_lines`, `fs_grep_files`, `fs_regexp_lines`, `fs_read_symbol`, `x86_disassemble`, `elf_list_sections`, `elf_list_symbols`, `hexdump`, and `hexinspect` previously opened files multiple times per call (`is_binary_file`, line counting via `std::istreambuf_iterator`, `std::getline`, and `std::istringstream` copies). Sharing `mapped_file` across these tools eliminates heap allocations on non-matching grep files and turns repeated `fs_read_lines` calls on the same file into $O(1)$ slice lookups.
- **Bounding Readahead Below Cache Capacity**: Queuing an entire repository's file list into a background prefetch thread would evict earlier prefetched entries from the 64-entry LRU cache before the consumer reaches them. Bounding the prefetch queue to `k_max_prefetch_window` (24) and preferring already-consumed entries during LRU eviction ensures `unused_prefetch_evictions` remains zero during `fs_grep_files` sweeps.
- **Static Destruction Order Between `project_manager` and `mapped_file_cache_manager`**: Function-local `static` singletons are destroyed in the reverse order of their first initialization. If `project_manager::get_instance()` is initialized before `mapped_file_cache_manager::get_instance()`, `~mapped_file_cache_manager()` runs first during `atexit`, and a subsequent call to `mapped_file::shutdown_cache()` inside `~project_manager()` would call `.clear()` on already-destroyed `std::unordered_set`/`std::unordered_map` members, corrupting adjacent heap chunk metadata. Guarding the static entry points with an atomic `g_cache_destroyed` flag set in `~mapped_file_cache_manager()` prevents post-destruction access regardless of singleton initialization order.
