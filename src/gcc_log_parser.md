# GCC and Clang Build Log Parser (`gcc_log_parser`)

## Goals
The `gcc_log_parser` class (`src/gcc_log_parser.h`, `src/gcc_log_parser.cpp`) implements the `build_log_parser` interface to extract structured compiler diagnostics (`build_error`) from streaming build output generated by GCC, Clang, and compatible toolchains.

## Architecture and Constraints
- **Diagnostic Regex Matching**:
  - Matches diagnostic lines conforming to `^(.*?):([0-9]+):([0-9]+): (fatal error|error|warning): (.*)$`.
  - Non-greedy filename capture supports paths containing spaces and Windows-style drive letters (e.g., `C:/...`).
  - Supports `fatal error`, `error`, and `warning` severities.
  - Subordinate messages like `note:` or `remark:` are excluded from primary error list navigation.
- **Coordinate Conversion**:
  - GCC/Clang reports 1-based line numbers and column numbers. These are converted to 0-based indexing for internal editor buffer navigation.
  - `end_column` is set to 0, signaling the editor UI to highlight the entire line.
- **Path Resolution & Validation**:
  - If the path is relative, it is resolved against `config_manager::get_instance().get_build_directory()` using `fs_utils::safe_absolute`.
  - Errors are only recorded if the referenced file exists on disk (`std::filesystem::exists`), preventing nonexistent paths or terminal artifacts from generating phantom error markers.

## Lessons Learned
- **Missing Header Inclusions (`fatal error`)**: GCC and Clang report `#include` failures as `fatal error: <header>: No such file or directory`. Without matching `fatal error` in the severity pattern, missing header failures are silently ignored by the build error manager.
- **RAII Temporary Directory Isolation in Tests**: File-backed parser tests must clean up temporary test files and directories via RAII guards to avoid leaving dirty artifacts across test runs or during assertion aborts.
