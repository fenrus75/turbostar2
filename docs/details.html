1. Tool Families

How to provide a large, rich toolset to an agent without context bloat

Problem Statement

When an agent framework provides a very large set of tools to the LLM, model performance tends to degrade. Not only does a large toolset take up a lot of tokens, but models—especially quantized ones—often start hallucinating tool parameters or even tool names.

Solution: Tool Families

Turbostar groups tools into "tool families", most of which are not enabled by default. The LLM is provided a tool call to activate a tool family, along with a list of available families including descriptions that inform the LLM when to activate a specific family.

To illustrate this concept better, below is a list of some available tool families in Turbostar. Plugins can also register their own tool families dynamically.

  • git: All the tool calls to interact with the Git version control system.
  • hexedit: Tools to analyze, dump, and edit binary files.
  • image: Image processing tools (zoom, rotate, crop, format conversion, etc.).
  • x86asm: Tools to assemble, disassemble, and analyze x86/x64 machine code.

2. Catching Crashes & GDB Integration

Providing the agent and the user automatic backtraces and debuggable coredumps.

Steering the Agent

Native applications crash for many reasons (bad pointers, failed assertions). Many LLMs will try to guess the issue based on minimal logs, jumping to incorrect conclusions on complex bugs. Turbostar uses the Least Friction Principle: we inject the crash root cause directly into the execution tool output so the LLM has zero friction diagnosing it.

Example: Steering via agent_wait_for_app

When an application crashes, the agent receives an immediate, structured notification explicitly telling it how to retrieve the coredump:

{
  "crash_notification": "\n\nCRASH DETECTED: Application crashed (Crash ID: 1028928).\nSummary: assertion fail at ../main.cpp:8 `c != NULL` in void foo(char*)()`\nPlease use 'crashdump_get_info' with crash_id '1028928' to investigate stack trace and details.",
  "is_alive": false,
  "status": "ended"
}

Coredumps & Agent GDB Architecture

Generating coredumps is handled transparently via libturbocatch.so. But more importantly, the AI agent is given native GDB integration to investigate the dump.

Instead of forcing the LLM to run bash commands blindly, Turbostar acts as a mediator: the LLM sends commands (like info locals), and Turbostar pipes them through gdbserver to the application, parsing the output back cleanly to the LLM. 

// Example GDB Tool Call Result:
frame 11
#11 0x0000560239369191 in foo (c=0x0) at ../main.cpp:8
8 assert(c != NULL);
(gdb) info locals
buffer = "\002V\000"
(gdb) info args
c = 0x0

3. Built-in Performance Profiling

Bridging the gap between Linux perf data and LLM token limits.

Why Linux Perf is a Bad Fit for LLMs

Performance matters for native applications. While the Linux perf CLI tool is incredibly powerful, it is not a natural fit for LLMs:

  • Assembly vs Code Lines: perf operates primarily on assembly instructions. LLMs "think" in terms of high-level functions and source code lines.
  • Messy Parsing: perf output is designed for humans and varies wildly by version.
  • Massive Data: Raw performance profiling generates a massive amount of data. Feeding raw perf record logs into an LLM will instantly exhaust the context window.

The Turbostar Solution

To provide LLM-friendly profiling, Turbostar invokes the perf_event_open system call directly via libturbocatch.so.

Instead of raw logs, the agent receives condensed summaries (agent_get_profile_summary) showing only the top bottleneck functions. If the agent wants to drill down, it calls agent_get_profile_details to get exact line-by-line attribution of CPU samples directly mapped to the source code—costing only a few hundred tokens instead of millions.

4. Compiler Output Awareness

Reduce context-token consumption of compiler and test output.

Compiler Output

Compiling software can generate verbose output—for example, Meson emits over 1,000 lines when compiling Turbostar. Most of those lines (successful, warning-free build steps) offer no value to the LLM while consuming substantial context window tokens.

Turbostar parses standard output from common build systems like Meson and filters out noise lines. While this applies primarily to compiled languages, the reduction in context-consuming tokens is typically between 20x and 50x!

Test Suite Output

Similarly, test suite output follows standard formats. Turbostar filters out successful tests, presenting only test failures for the LLM to analyze.
