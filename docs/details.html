1. Tool families

How to provide a large, rich toolset to an agent without context bloat

Problem statement

When an agent framework provides a very large set of tools to the LLM, model performance tends to degrade. Not only does a large toolset take up a lot of tokens, but models - especially quantized ones - often tend to start hallucinating tool parameters or even tool names.

Solution: Tool families

Turbostar groups tools into "tool families"; most of which will not be enabled by default. The LLM is provided a tool call to activate a tool family, and is provided a list of available families, including descriptions that inform the LLM when to activate the specific tool family.

To illustrate this concept better, below is a list of some of the available tool families in Turbostar. Note that plugins can register their own tool families dynamically.

  • git - all the various tool calls to interact with the git version control system
  • hexedit - various tools to analyze, dump and edit binary files
  • image - various image processing tools (zoom, rotate, crop, format conversion, etc)
  • x86asm - tools to assemble, disassemble and analyze x86 code

In agent definition files (agent.md etc), we extend the agent specification with an option that specifies which tool families are enabled by default for this agent. For example, a coding agent will have the "git" family enabled, while an agent working on webpages may have the "image" tool family enabled by default, but not the git one.

2. Catching Crashes

Providing the agent and the user automatic backtraces and debuggable coredumps.

Backtraces

Native (C, C++, etc) applications can "crash" for many reasons, from chasing a bad pointer, to hitting an assert() to not handling an exception. Turbostar will wrap test and application execution with a special LD_PRELOAD library (libturbocatch.so) that will intercept key signals and will (carefully) write a stack trace to a dedicated location.

The main turbostar application will use this backtrace file to decode the addresses (something that is not safe in signal handlers) to turn this into an actionable report for the user and the AI agent. Turbostar keeps an internal database of crashes, and the user and the AI agent can go through these and look at the details at any time. For the user of the editor, backtrace elements have a "go to source" option for those parts of the backtrace that are within the project.

AI agents get automatically notified that a crash happened, with instructions on how to retreive the details for the crash.

Coredumps

Coredumps are the ultimate data for analyzing crashing, containing a full copy of the memory of the application at the time of crash. However, reliably getting a coredump file turns out to be a nightmare of Linux distribution specific mess. Systemd's coredumpctl? Not on Debian. Running ChromeOS? Just forget it. Running in a container, well, all bets are off.

Turbostar will use coredumpctl if it is available, but in addition, libturbocatch.so will trigger the execution of gdb's "gcore" application and make a kernel-independent coredump file of the crashing application. While neither gcore nor coredumpctl each are perfect, the dual-attempt approach means that in practice, coredumps will be available for each crash;

From the backtrace details, an one click "gdb window for the coredump" is available to the human user of the editor, while for AI agents, a fully interactive gdb session is one tool call away.
